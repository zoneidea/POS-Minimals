# 08 — Security, Encryption & Multi-Tenant Isolation

> **Implementation scope (Phase 1, 2026-10-11):** พัฒนาเฉพาะ **React Web App + Node.js/Express API + Supabase** ใน Repository [`zoneidea/POS-Minimals`](https://github.com/zoneidea/POS-Minimals). JavaFX Desktop และ Native Mobile App **ยังไม่ต้องพัฒนา ไม่ต้องสร้าง SDK/Installer หรือเพิ่มเป็น Gate ใน CI/UAT รอบนี้**; ออกแบบ API ให้ขยายในอนาคตได้เท่านั้น.

## 1. Threat model (high priority)
- Cross-tenant data read/write by guessing product/sale IDs or editing `org_id`
- Unauthorized employee attempting reports, void or inventory edit
- Double-click sale, network retry, concurrent stock depletion, race between void and sale
- XSS/CSRF/session theft, leaked service keys, credential stuffing, insecure uploads
- Sensitive information leaked through logs, downloadable exports, cached data or storage signed URLs

## 2. Tenant boundary
- `org_id` UUID generated by DB and globally unique; every business row must belong to exactly one org
- Auth user identity is global `auth.users` managed by Supabase; business ownership stored in `organization_members`
- Every request resolves `auth.uid()` and `org_id` via `ACTIVE` membership and checks role; no trust in request-supplied tenant id
- Query scoped by `org_id`; composite FK `(org_id, referenced_id)` blocks cross-tenant reference integrity bugs
- RLS enabled for all exposed org tables and Storage, plus least-privilege grants and narrow RPC permissions
- Tenant-qualified cache key `tenant:<orgId>:...`; never cache entire cross-tenant query as a global key
- Cross-tenant tests required for `GET/POST/PATCH/DELETE`, reports, CSV/XLSX exports, image URLs and RPCs

## 3. Authentication and password handling
- Use Supabase Auth password hashing/storage and reset flow; no custom plaintext passwords or encryption reversible storage
- Unique email for login globally (normalize lowercase, trim); username can duplicate as display label
- Password **not required to be unique across every user's account**: comparing plaintext or deterministic hashes across users creates avoidable privacy/security risk; enforce sufficient strength, breached password protection if available, and prevent reusing own prior passwords if policy requires
- Do not log password/auth token; HTTPS only; apply auth/signup/login rate limits
- For session storage on SPA apply CSP/XSS precautions and follow Supabase Auth supported session pattern; never put credentials in localStorage cart record
- Token validity and role/active membership checked server-side each request; revoked/suspended staff denied immediately (not by JWT role alone)

## 4. Secrets, encryption, API
- In transit HTTPS/TLS; at rest use Supabase managed DB/storage encryption; encrypt extra sensitive secrets with managed key handling where business need dictates
- Supabase publishable/anon key may be used only as public identifier with correct RLS. **Service role / secret API keys must never reach browser** because they bypass RLS
- Secret keys set in Vercel environment vars; no commits, logs, client-side build env exposure
- Zod validation on server; param binding/parameterized SQL, no string interpolated SQL; output escaping against XSS
- Helmet/security headers, strict CORS origin, body size limit, upload mime/size validation, strong CSP, appropriate SameSite and CSRF protection if cookie auth is chosen
- Rate-limit sensitive mutations/auth; behind Vercel use infrastructure-compatible rate limiter (process-local limit alone does not enforce global rate limits)

## 5. Transactions and audits
- Stock, checkout, void, reverse only through DB transactions protected by locks and constraints
- Monetary totals recalculated by DB/backend; client supplied prices/tax ignored
- Log events with `requestId`, actor, org, action, entity id, result, timestamp; redact data as appropriate
- Before/After logs retain integrity; only OWNER can view; reverse creates linked new event
- Do not allow generic direct update/delete on `sales`, `sale_items`, `payments`, `stock_movements`, `product_audit_logs`

## 6. Images and Excel
- Product images store in `product-images/<orgId>/<productId>/<opaque-id>.<ext>`; validate org on upload/read, MIME, max size, quota, optional content scanning
- Public bucket is convenient but leaks product images across tenants if URL known; for isolation requirement prefer private bucket with signed read URLs or controlled proxy
- Spreadsheet sanitize formula injection on export and imported text; enforce max rows/file bytes, read streaming/worker within runtime limit

## 7. Operational security
- Separate Supabase dev/staging/prod projects where practical; least privilege CI deployment keys
- Scheduled database backups, tested restore, migration review and audit retention policy
- Alerts for unauthorized access, repeated auth failures, API 5xx, database lock waits and unusual void volume
- Do not claim password reuse can be globally prevented without security and privacy tradeoffs; see `13_OPEN_DECISIONS.md`

## 8. Required acceptance proofs
- Org A token cannot view/edit/export org B's sale, products, images, audit, staff or reports
- Employee cannot void (403); Accountant cannot checkout (403); suspended user denied (403)
- Browser bundle inspection reveals no Supabase secret/service key or DB connection string
- Force same sale idempotency key 10x => only 1 sale and 1 inventory decrement


## Future client access policy (reference only; no native implementation in Phase 1)
- All business clients use `Authorization: Bearer` from Supabase Auth public flows. API validates cryptographic JWT and resolves live member/role for each operation; JavaFX and mobile do not authenticate by device ID, platform header, ORGID, CORS origin or IP.
- Only public Supabase publishable/anon key may appear in distributed desktop/mobile build; **never** embed Supabase service_role/secret, direct DB credentials or Vercel deployment secrets in app packages or source maps.
- Web: restrict origins with exact CORS allowlist, CSP, HTTPS, XSS protection. Browser token persistence has XSS tradeoff; minimize exposure and avoid logs. Native: keep refresh credentials in secure OS storage (Windows Credential Manager/macOS Keychain/Android Keystore/iOS Keychain) or memory-only with re-login; not plaintext config/SQLite.
- Auth token refresh single-flight per client; refresh on 401 once; role/membership revocation detected on next server request. Device time skew must not permit bypassing server-side void window.
- Use signed/short-lived authorized upload URLs bound to org + validated object path; enforce Storage RLS where applicable; never accept arbitrary owner-controlled URL fetch (SSRF).
- Request ID + actor/org id in server audit metadata, but redact JWT, refresh token, passwords, full card/tax PII; no sensitive URL query string for authorization.
- Native client certificate validation on by default; no global trust-all SSL setting, no plaintext HTTP production fallback.
- Backend CORS only affects browser JS; Java/native callers bypass CORS enforcement, so all actual security stays in bearer validation+membership+RLS.
