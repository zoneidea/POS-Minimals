# แผน KidTang Module Marketplace

วันที่: 2026-10-18
สถานะ: **ข้อเสนอเพื่อพิจารณา — ยังไม่เริ่มพัฒนา**

ผู้ใช้ต้องการ Marketplace ภายใน KidTang สำหรับโมดูลที่ทีมพัฒนาสร้างเอง ให้ร้านซื้อและเริ่มใช้ได้หลังชำระสำเร็จ งานนี้จัดทำแผนเท่านั้น ไม่เปลี่ยนโค้ด ฐานข้อมูล สิทธิ์ ระบบรับเงิน หรือ deployment การเปลี่ยนโครงสร้างและ migration ต้องได้รับอนุมัติก่อนลงมือ

## 1. แนวทางและขอบเขต

- ใช้ React/Express/Supabase และ repository/deployment ร่วมเดิม
- คงระบบหลักที่ใช้อยู่เป็นฟังก์ชันฟรี ไม่ย้ายฟังก์ชันเดิมไปล็อกขายโดยอัตโนมัติ
- ทีม KidTang พัฒนาและ deploy โมดูลล่วงหน้า จากนั้นเผยแพร่รายการใน Marketplace เมื่อพร้อมขาย
- การซื้อเปิดสิทธิ์ของร้าน ไม่ต้องติดตั้งโปรแกรมหรือ deploy ใหม่สำหรับร้านแต่ละราย
- ไม่ดาวน์โหลด/รันโค้ดหรือ SQL จากผู้ซื้อหรือผู้ขายภายนอก
- รุ่นแรกขายเฉพาะโมดูลของทีมเรา ไม่ทำระบบผู้ขายบุคคลที่สามหรือแบ่งรายได้ให้ผู้ขาย
- รูปแบบซื้อขาด/ตามระยะเวลาและราคาเป็นเรื่องที่ต้องยืนยัน ไม่ถือว่าตัดสินใจแล้ว

## 2. หน้าจอและการใช้งาน

| ส่วน | เนื้อหา/การทำงาน |
|---|---|
| Marketplace | โมดูลพร้อมขาย ภาพตัวอย่าง คำอธิบาย ราคา รูปแบบสิทธิ์ และสถานะซื้อแล้ว |
| รายละเอียดโมดูล | ประโยชน์ ความสามารถ เงื่อนไข สิทธิ์ผู้ใช้ที่เกี่ยวข้อง ความพร้อม/ข้อจำกัด และปุ่มซื้อ |
| Checkout Add-on | ร้านที่ซื้อ โมดูล ราคา/ภาษีตามนโยบายที่อนุมัติ ยอดชำระ ช่องทางชำระ และสถานะ |
| โมดูลของร้าน | สิทธิ์ที่ซื้อ สถานะ วันเริ่ม/สิ้นสุด เปิดใช้งาน ตั้งค่า และต่ออายุเมื่อรองรับ |
| ประวัติการซื้อ | เลขที่คำสั่งซื้อ วันซื้อ ยอด สถานะ และเอกสารการซื้อ |
| จัดการ Marketplace ของแพลตฟอร์ม | สร้างรายการ ราคา เผยแพร่/หยุดขาย และตรวจสอบคำสั่งซื้อ/สิทธิ์ |

ใช้ธีมและ responsive ของระบบเดิม การซื้อและคืนเงินใช้ confirm ส่วนผลสำเร็จ/ข้อผิดพลาดใช้ SweetAlert2 ตามแนวทางปัจจุบัน การปิดหน้าต่างชำระเงินต้องไม่ถูกตีความว่าผู้ให้บริการยกเลิกเงินแล้ว

## 3. สิทธิ์และขอบเขตร้าน

- สิทธิ์ซื้อผูกกับ org_id ของร้าน ไม่ผูกกับอีเมลผู้ซื้อ จึงคงอยู่เมื่อร้านเปลี่ยนพนักงาน
- OWNER ซื้อ ต่ออายุ และเปิด/ปิดการใช้งานโมดูลของร้าน
- ACCOUNTANT ดูประวัติการซื้อ/เอกสารตามขอบเขตที่อนุมัติ แต่ซื้อหรือเปลี่ยนสิทธิ์ไม่ได้
- EMPLOYEE ใช้เฉพาะความสามารถที่ role อนุญาต ภายใต้โมดูลที่ร้านมีสิทธิ์ ไม่เห็นการจัดการซื้อ
- สูตรการอนุญาตคือ สมาชิกยังใช้งานได้ + ร้านมีสิทธิ์โมดูล + โมดูลเปิดใช้งาน + role อนุญาตการกระทำ
- เจ้าของร้านทั่วไปไม่ใช่ผู้ดูแล Marketplace ส่วนกลาง ต้องออกแบบสิทธิ์ทีมแพลตฟอร์มแยก ไม่ให้ OWNER ของร้านอ่านข้อมูลข้ามร้าน และไม่ hardcode อีเมลผู้ดูแล
- ซ่อนเมนูอย่างเดียวไม่เพียงพอ Backend ต้องบังคับสิทธิ์กับ API ของแต่ละโมดูลด้วย

## 4. ขั้นตอนซื้อและเปิดใช้

1. เจ้าของเลือกร้านและโมดูล ระบบตรวจสถานะพร้อมขายและสิทธิ์เดิม
2. Backend อ่านราคา/เงื่อนไขจากรายการที่เผยแพร่ แล้วสร้าง order พร้อม snapshot ราคา สกุลเงิน และเงื่อนไข ไม่รับยอดจาก browser เป็นข้อยุติ
3. สร้างการชำระเงินที่ผูกกับ order และแสดงยอด/QR ตามช่องทางที่อนุมัติ
4. Backend ตรวจผลกับผู้ให้บริการ โดยเทียบ payment ID, reference, ยอด, สกุลเงิน และสถานะสำเร็จ
5. บันทึก order ที่ชำระแล้วและสิทธิ์โมดูลภายในธุรกรรมฐานข้อมูลเดียวกัน พร้อมบันทึกหลักฐานการชำระและ audit
6. ล้าง cache/context ที่เกี่ยวข้อง คืนรายการสิทธิ์ใหม่ และแสดงปุ่มเริ่มใช้โดยไม่ต้อง logout
7. หากโมดูลต้องตั้งค่าก่อนใช้ ให้เปิดขั้นตอนตั้งค่าโดยรักษาสถานะซื้อสำเร็จไว้

คำสั่งซื้อ/การยืนยันต้องมี idempotency การกดซ้ำ callback ซ้ำ หลายแท็บ หรือ response หายต้องได้สิทธิ์ชุดเดิม ไม่เก็บเงิน/เปิดสิทธิ์ซ้ำ ผู้ซื้อที่มีสิทธิ์ซื้อขาดอยู่แล้วต้องได้รับสถานะซื้อแล้ว ไม่สร้าง QR ใหม่โดยไม่จำเป็น

## 5. การชำระเงินส่วนกลาง

- เงินซื้อ Add-on เป็นรายได้ของแพลตฟอร์ม KidTang ต้องใช้ merchant/บัญชีรับเงินของแพลตฟอร์มที่อนุมัติ
- แยกจาก Payment Gateway ที่ร้านใช้รับเงินลูกค้าหน้า POS ร้านไม่จำเป็นต้องเปิด Gateway ของร้านเพื่อซื้อโมดูล
- ไม่สร้าง sale/stock movement ใน POS ของร้านจากการซื้อ Add-on และไม่รวมยอดนี้ในรายงานยอดขายร้าน
- อาจนำ adapter/รูปแบบตรวจสอบ ReservePay เดิมมาใช้ซ้ำได้ แต่ต้องประเมินความสามารถและบัญชีส่วนกลางก่อน ไม่สมมติว่ารองรับ recurring, webhook หรือ refund แล้ว
- รุ่นแรกเสนอให้รับชำระเป็นครั้งต่อ order หากเลือกสิทธิ์รายเดือน/ปี ให้เริ่มด้วยเจ้าของกดต่ออายุเอง การหักเงินอัตโนมัติเป็นงานแยกภายหลัง
- ถ้าผู้ให้บริการรองรับ webhook ที่ตรวจสอบที่มาได้ ให้ใช้เพื่อยืนยันแม้ปิด browser พร้อมงานตรวจสอบรายการค้าง หากไม่รองรับ ต้องกำหนด server reconciliation ที่เชื่อถือได้ก่อนเปิดขาย
- หากจ่ายแล้วแต่ระบบยังยืนยัน/บันทึกไม่ได้ ให้แสดงรอตรวจสอบและกู้คืนจาก order เดิม ห้ามแนะนำให้จ่ายใหม่ทันที
- QR หมดอายุ/ผู้ใช้กดยกเลิก แต่พบเงินเข้าภายหลัง ต้องเข้าสู่กระบวนการตรวจสอบตามนโยบาย ไม่ทิ้งหลักฐานหรือเปิดสิทธิ์ผิดร้าน
- กำหนดภาษี เอกสารการซื้อ เงื่อนไขคืนเงิน และผลต่อสิทธิ์กับผู้รับผิดชอบก่อนเปิดรับเงินจริง ไม่ใช้ค่าธรรมเนียม POS 1.5% เป็นค่าธรรมเนียม Add-on โดยอัตโนมัติ

## 6. การออกแบบโมดูล

แต่ละโมดูลมีรหัสคงที่ เวอร์ชัน route/เมนู ความสามารถตาม role และสถานะพร้อมใช้งาน เชื่อมกับ registry ในโค้ดที่ทีมดูแล ไม่รับชื่อไฟล์หรือคำสั่งรันจากฐานข้อมูล Marketplace

- เมนูและหน้าจอโหลดเฉพาะส่วนที่จำเป็นผ่านแนวทาง lazy load เดิม
- ตารางข้อมูลธุรกิจของโมดูลมี org_id และ RLS เช่นเดียวกับระบบหลัก
- Migration ใช้ DatabaseInitializer/versioned migrations เดิม และต้องพร้อมก่อนประกาศโมดูลขาย ไม่รัน SQL จาก browser ตอนซื้อ
- ปิดการขายโมดูลไม่ได้หมายถึงเพิกถอนสิทธิ์ลูกค้าเดิม ต้องกำหนดการรองรับรุ่นเก่า/ยุติบริการแยก
- สิทธิ์การเป็นเจ้าของกับการเปิด/ปิดใช้งานเป็นคนละสถานะ ปิดใช้งานแล้วเปิดใหม่ได้ตามสิทธิ์เดิม
- เมื่อหมดอายุหรือระงับ ไม่ลบข้อมูลที่โมดูลสร้าง ต้องกำหนดสิทธิ์อ่าน/ส่งออกข้อมูลเดิมก่อนเปิดขาย
- โมดูลเสียหรือปิดชั่วคราวต้องไม่ขัดขวางการขายหลัก โดยเฉพาะ POS/ตะกร้า/การพิมพ์

## 7. ข้อมูลที่เสนอเพิ่ม — ยังไม่สร้างตาราง

| กลุ่มข้อมูล | หน้าที่ |
|---|---|
| modules | รหัส ชื่อ รายละเอียด เวอร์ชัน สถานะการเผยแพร่ |
| module_prices | รุ่นราคา สกุลเงิน รูปแบบสิทธิ์/ระยะเวลา ช่วงที่ใช้ราคา |
| addon_orders / order_items | คำสั่งซื้อ org ผู้ซื้อ snapshot ราคา/เงื่อนไข และ idempotency |
| addon_payments / payment_events | payment reference หลักฐานสถานะ เหตุการณ์ซ้ำ และการกู้คืน |
| org_module_entitlements | สิทธิ์ของร้านต่อโมดูล วันเริ่ม/สิ้นสุด ที่มาจากคำสั่งซื้อ สถานะและเวอร์ชัน |
| org_module_settings | การเปิด/ปิดใช้และค่าตั้งต้นของโมดูลต่อร้าน |
| addon_adjustments | หลักฐานคืนเงิน/ปรับสิทธิ์แบบเพิ่มประวัติ ไม่แก้ประวัติการซื้อเดิมทับ |

ชื่อและโครงสร้างเป็นข้อเสนอ ต้องทบทวน constraints, indexes, encryption, RLS และ migration/rollback ก่อนพัฒนา เก็บข้อมูลส่วนบุคคลเท่าที่จำเป็นและเข้ารหัสตามมาตรฐานเดิม

ราคาและเงื่อนไขในคำสั่งซื้อเดิมคงเดิมเมื่อผู้ดูแลเปลี่ยนราคาขายใหม่ ประวัติการเงิน/สิทธิ์ไม่อยู่ในงานลบ Application Logs 30 วัน ส่วน request/activity diagnostics ยังคง 30 วันและไม่เก็บ secret/QR/ข้อมูลบัญชีเต็ม

## 8. API ที่เสนอ — ยังไม่ใช่สัญญาที่เผยแพร่

รักษาการแยก API ลูกค้าและ management เดิม โดยกำหนด schema ใน OpenAPI ก่อนเริ่มทำ frontend:

| API ลูกค้า | ข้อมูลหลัก |
|---|---|
| อ่านรายการ/รายละเอียดโมดูล | moduleCode, version, price, billingType, availability, currentEntitlement |
| สร้างคำสั่งซื้อ | รับ moduleCode/priceId และ idempotency key; org/ราคาอนุมานจากบริบทที่ตรวจสอบแล้ว |
| เริ่มชำระ order | คืน orderId, payment reference, amount, currency, expiry และข้อมูลแสดงการชำระที่ปลอดภัย |
| อ่าน/ยืนยันสถานะ order | คืน status และสิทธิ์ที่เปิดแล้วหลัง Backend ตรวจสอบ ไม่รับ paid=true จาก client |
| อ่านโมดูลของร้าน | entitlementStatus, enabled, startsAt, expiresAt, permittedActions |
| เปิด/ปิดใช้โมดูล | OWNER เท่านั้น ตรวจสิทธิ์ซื้อและ version ก่อนเปลี่ยน |

Management API แยกสำหรับรายการโมดูล รุ่นราคา การเผยแพร่ ค้น order ที่ต้องตรวจสอบ และการปรับสิทธิ์พร้อมเหตุผล/audit ผู้ดูแลไม่มีสิทธิ์ปลอมหลักฐานการชำระเพียงเพื่อแก้สถานะให้ผ่าน

## 9. Cache และประสิทธิภาพ

นำกลไก cache ที่มีอยู่มาใช้ตามความเหมาะสม ไม่เริ่มโครงการย้าย region/ปรับโครงสร้าง Redis ที่ผู้ใช้พักไว้:

- โหลดบริบทสิทธิ์โมดูลรวมต่อร้าน และ reuse ใน request เดียว ไม่ query ซ้ำทุก component
- key มี org และเวอร์ชันสิทธิ์ ป้องกันข้อมูลสิทธิ์ข้ามร้าน
- หลังซื้อ เปิด/ปิด ระงับ คืนเงิน หรือต่ออายุ ต้อง invalidate/update context หลัง commit
- ตรวจ expiresAt แม้ข้อมูลมาจาก cache; ไม่ cache สิทธิ์จนกว่าจะ logout
- กำหนดเพดานความล่าช้าในการเพิกถอนและทดสอบข้าม instance ก่อนเปิดขาย งานเปลี่ยนข้อมูลสำคัญต้องไม่อาศัย client/cache ที่เพิกถอนแล้ว
- หากยืนยันสิทธิ์ไม่ได้ ให้ปฏิเสธงาน Add-on อย่างปลอดภัย โดยไม่บล็อกฟังก์ชันฟรีที่ไม่เกี่ยวข้อง

## 10. แผนส่งมอบทีละระยะ

1. **ยืนยันกติกาธุรกิจ:** โมดูลแรก รูปแบบสิทธิ์ ราคา บัญชีแพลตฟอร์ม เอกสาร/ภาษี คืนเงิน และผลเมื่อสิ้นสุดสิทธิ์
2. **วางพื้นฐานโมดูล/สิทธิ์:** registry, schema/RLS, owner/platform permissions, guards และ cache invalidation ให้ทดสอบกับโมดูลแรกได้ก่อน
3. **Marketplace และการซื้อ:** catalog/detail, orders, payment verification/recovery, ประวัติซื้อ และหน้าจัดการทีมแพลตฟอร์ม
4. **เปิดใช้งานอัตโนมัติ:** transaction paid→entitlement, เมนู/route, onboarding และการเปิด/ปิดโมดูล โดยรักษา POS เดิม
5. **ทดสอบและทดลองขาย:** sandbox/บัญชีทดสอบถ้ามี ตามด้วยรายการจริงที่อนุมัติ กลุ่มร้านทดลอง แล้วจึงเปิดทั่วไป

ส่งมอบโมดูลแรกครบวงจรก่อนเพิ่มโมดูลถัดไป ไม่กำหนดวันส่งมอบจนกว่าจะเลือกโมดูลและรูปแบบการขาย

## 11. เกณฑ์รับงานก่อนเปิดขาย

- เจ้าของซื้อแล้วเริ่มใช้ได้โดยไม่ logout/redeploy รายร้าน; บัญชี/พนักงานซื้อไม่ได้
- ร้านที่ไม่ได้ซื้อเรียก API Add-on โดยตรงไม่ได้ และซื้อให้ร้านอื่นจากการแก้ payload ไม่ได้
- ใช้ entitlement และ role ร่วมกัน ไม่ให้การซื้อเพิ่มสิทธิ์ของพนักงานเกิน role
- จ่ายสำเร็จครั้งเดียวเกิด order/สิทธิ์ครั้งเดียว แม้หลายแท็บ/confirm พร้อมกัน/notification ซ้ำ
- สร้าง QR อย่างเดียว จ่ายไม่ครบ ผิดสกุลเงิน ผิด merchant หรือยืนยันไม่ได้ ต้องไม่เปิดสิทธิ์
- ปิด browser/เครือข่ายขัดข้องแล้วกู้คืน order เดิมได้ โดยไม่ต้องจ่ายซ้ำ
- ซื้อขาดซ้ำ คืนเงิน หมดอายุ ต่ออายุ และระงับ เป็นไปตามนโยบายที่อนุมัติ และ cache ไม่คงสิทธิ์ที่เพิกถอนเกินเพดานที่กำหนด
- ราคาเปลี่ยนไม่เปลี่ยน snapshot ของ order เดิมและไม่เปิดสิทธิ์ซ้ำ
- ไม่ปนเงิน Add-on กับยอดขาย/สต็อกร้าน และไม่ลบประวัติการเงินใน retention 30 วัน
- rollback/ปิดโมดูลที่มีปัญหาได้ โดยไม่ทำข้อมูลลูกค้าหายหรือทำ POS เดิมใช้ไม่ได้
- ยืนยันผลชำระ/เอกสาร/บัญชีรับเงินและ live UAT ก่อนเปิดรับซื้อทั่วไป

## 12. ข้อความหน้าเว็บและเรื่องที่ต้องยืนยัน

ก่อนเปิด Marketplace ต้องปรับ Landing/FAQ/เงื่อนไขที่ปัจจุบันใช้ “ใช้ฟรีทุกฟังก์ชัน” ให้ชัด เช่น “ระบบหลักใช้ฟรี · เลือกซื้อโมดูลเสริมได้” โดยไม่กระทบสิทธิ์ฟังก์ชันเดิมของลูกค้า รอบนี้ยังไม่แก้ข้อความจริง

ข้อเสนอเริ่มต้น: ขายต่อร้าน ทีม KidTang เป็นผู้ขายรายเดียว เจ้าของซื้อ เปิดสิทธิ์หลังตรวจเงินสำเร็จ และเริ่มด้วยหนึ่งโมดูล ส่วนรูปแบบราคา/ระยะเวลายังไม่ถือว่าอนุมัติ

ต้องยืนยันก่อนเริ่มพัฒนา:
1. โมดูลแรกที่จะขายคืออะไร และความสามารถ/เกณฑ์รับงานของโมดูลนั้น
2. ซื้อขาด รายเดือน/รายปี หรือเลือกได้ต่างกันต่อโมดูล
3. merchant/บัญชีรับเงินส่วนกลาง พร้อมนโยบายภาษี/เอกสาร/คืนเงิน
4. ผู้ดูแล Marketplace ของทีมแพลตฟอร์ม และสิทธิ์ข้อมูลเดิมเมื่อหมดอายุ/ระงับ
